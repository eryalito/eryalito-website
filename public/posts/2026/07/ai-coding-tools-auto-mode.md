# Why I Am Worried About Auto Mode in AI Coding Tools

Have you ever been using your favorite (or the one your company pays for) AI coding tool and had it randomly try to access your passwords, keys, or private data? If you have, you're not alone — it has happened to me too. I was using Claude Code for debugging an error in a service, and when I pasted an error message, it tried to enumerate and connect to all Kubernetes clusters I have access to. Glad I was in manual mode and blocked it, but it was an interesting experience.

## What Is Auto Mode?

We're in mid-2026, and I won't argue how many devs are using AI tools, as I'm sure it's virtually all of us. I want to talk about a specific feature that is basically forced by all tools: auto mode. Let me ask Codex what auto mode is:

> Auto mode lets Codex edit files automatically while asking for approval before running shell commands

Except that's not what auto mode does. According to [OpenAI's own docs](https://learn.chatgpt.com/docs/agent-approvals-security), the Auto preset lets Codex read files, make edits, and run commands inside the workspace without asking. What it does ask approval for is editing outside the workspace or accessing the network. The behavior Codex just described to me is a different preset. So the tool got its own permission boundary wrong.

Still, the pattern Codex described is a common implementation of auto mode: edits happen automatically, but shell commands are approved manually, perhaps configured via a whitelist regex or simply running in "full access" mode, where all commands are allowed. Now, let's see what Claude has to say about auto mode:

> Auto mode: Claude runs without routine permission prompts — file edits and shell commands. Instead of asking you, a separate classifier model reviews each action before it runs and blocks anything that escalates past your request, touches unrecognized infra, or looks driven by hostile content Claude read.

Again, not quite. Per [Claude Code's docs](https://code.claude.com/docs/en/permission-modes), file edits inside your working directory are auto-approved and never reach the classifier at all, so shell commands and network calls are the part it actually reviews. And the answer left out the sentence that comes right after in those same docs: explicit `ask` rules still force a prompt, even in auto mode. Two tools, two wrong descriptions of their own permission boundary.

In other words, auto mode is a feature that lets the tool run most things without direct approval, with hardcoded guidelines or a classifier model acting as a second gatekeeper behind your own permission rules. I have two questions. First, is it possible to use these tools without auto mode? Second, can we trust the classifier model to approve or block commands correctly?

## The Burden of Approval

Auto mode is the natural evolution of coding tools since the moment they started having the ability to run shell commands. Devs are humans, and we humans are lazy, so the manual review of every single command the tools want to run is unrealistic. Even now, intelligent tools don't even "read" files, they read diffs, grep sections of files, or even just `find` specific files or directories. All of this requires command approval, and reviewing it is not only time-consuming but mentally exhausting. That's why, since day one, AI agents have been implementing some kind of auto mode, from regex whitelists to full access, and now a second model that reviews actions before they run.

Even the "traditional" solution is simple and solves the problem: configure your whitelist or manually approve each command. But, in practice, it is obviously not a solution: manual approval is a burden, and regex can't cover all cases, as some commands are context-dependent. And even if you are willing to accept the work of manually approving every command, you have to know what the command is doing, and that requires a lot of knowledge about the system, the code, and the context. In other words, you have to be an expert in the system you are working on, and even then, you can make mistakes.

Let's be real for a second. Is the average developer going to be able to review every random and obscure command that the AI is trying to run? Of course not — myself included. I have discovered commands and flags that I didn't even know existed. And don't get me started on when basically the AI tries to run a humongous inline `awk` command or Python script that does some obscure thing, and you have to read and understand the code to approve it.

This answers my first question: is it possible to not use auto mode? The answer is yes, on paper, but not in practice. The time wasted, mental fatigue, and lack of knowledge make it impossible to not use auto mode in any kind of competitive or real environment.

## The Trust Issue

I'm focusing on Claude's auto mode, as it's the one I have experience with, but it is not the only tool doing this. Codex ships [auto-review](https://learn.chatgpt.com/docs/sandboxing/auto-review), where approval requests get routed to a separate reviewer agent that is "itself a Codex agent with a narrower job than the main agent: decide whether a specific boundary-crossing action should run". Same idea, different implementations, but the trust question below applies to both. And there is a second trust question behind the first one: can we trust the companies behind these tools to not access our private data?

This raises two different types of trust concerns. On one side, we have the trust in the AI models themselves, which is what the classifier model is based on. On the other side, we have the trust in the company that provides the AI coding tool, which provides both models.

The idea with the classifier models is to add a second layer of security, potentially blocking malicious or unintended actions of the main model. However, similar to the main model, the classifier model is also a black box that can and will make mistakes. Anthropic, the company behind Claude, has published data on their [website](https://www.anthropic.com/engineering/claude-code-auto-mode) about how their approval model works. Here we can find some rough numbers about the model's performance, and they sit at around 17% false negatives and 0.4% false positives. This means that, in 17 out of 100 dangerous commands, the model will approve an action that it should have blocked, and in 4 out of 1000 legit commands, it will block an action that it should have approved. That's a non-negligible amount of false negatives, but I think an important detail is missing here: how does this compare to human reviewers? Anthropic points to a 93% user acceptance rate, but they don't provide any data on false positives or false negatives. I would like to see that data, as it would give us a better idea of how good the classifier model is compared to humans.

Which brings me back to the cluster enumeration from the start of this post. I was in manual mode, so I saw it and stopped it, and I still do not know what auto mode would have done. The docs cut both ways: the classifier is meant to block anything targeting unrecognized infrastructure, and by default it trusts your working directory and your repo's remotes and nothing else — but nothing the tool wanted to do was destructive either, since listing contexts reads a local config file and `kubectl logs` is a read. What bothers me is not the coin flip, it is what the classifier had to work with. I pasted an error message, and a README explaining that the app is deployed on Kubernetes was enough to send the tool looking for the service in every cluster it could reach. The error is in my own message, so the classifier saw it. The README is not: Anthropic are explicit that "the classifier sees only user messages and the agent's tool calls; we strip out Claude's own messages and tool outputs, making it reasoning-blind by design". That is a deliberate choice, and a defensible one, since it means a compromised file cannot convince the reviewer. But it also means the thing that pointed Claude at my clusters was invisible to the one component whose job is to ask whether that made sense.

Then, we have the traditional "vendor trust" problem, which is the trust in the company that provides the AI coding tool itself. Both models and the tool itself are provided by the same company, and we have to trust that they are not going to abuse our trust and access our private data. This is not just a valid concern; staying skeptical is good practice, as we have seen in the past that companies can and will abuse our trust. The problem is that we have no way of knowing if they are doing it or not, and we have no way of verifying it. If the malicious action is not a hallucination or misbehavior of the model, but a deliberate action of the company, we have no way of knowing it, let alone preventing it.

So, do we trust the classifier model? The answer is: it depends. It will depend on the model's performance, the company's reputation, and the data sensitivity. It's a tradeoff between convenience and security, and each user will have to make their own decision based on their own risk tolerance. If you ask me, I would say that at this point the classifier model is good enough for development and testing environments, but not for production environments. I use it while developing to run tests, linters, integration tests, and other tasks, but when touching production during incidents, I disable auto mode and review each command manually.

## How to Mitigate the Risks

Of course there are things that we can do on our end to mitigate the risks of using auto mode. First of all, there are some inherent risks that we can't mitigate, like the trust in the models and the company. The only way to mitigate these risks is to simply not use the tools, or use them in a very limited way without access to data, code, or systems that we don't want to be accessed. But there are some things that we can do to mitigate the risks, even without auto mode, like:

- Use a sandboxed environment even if the tool already has one. This is a good practice, as it will limit the potential damage that can be done by the tool, and it will also limit access to sensitive data.
- Purge sensitive data from environment variables, .env files, config files, and any other place where the tool can access it.
- Restrict network access: avoid running the tool in internal networks or with access to internal services.
- If it needs to connect to external services, use dedicated accounts or credentials with limited access and a custom identity. This will not only block unintended actions, but also give you traceability of the actions performed by the tool.

And in general, do not run the tool in environments where it could gain access to something you don't want it to access. Think of it, especially when running in auto mode, as an external person, and follow your standard practices for security and access control: you wouldn't give a random dev root access to your production environment, so why would you give it to the tool?

## What I Would Like to See in the Future

I think that companies realized long ago that the command approval problem needed a solution, and I think that the classifier model is a good step in the right direction. The core concept of the classifier model is good: leverage a second model, smart enough to understand the context and the intent of the command, to approve or block it accordingly. But I think that more effort should be put into it to make it more reliable, and to make it more transparent and open.

First of all, I would like to see the ability to __bring your own classifier model__, or at minimum the ability to implement something similar myself if needed. Claude Code supports HTTP hooks to block or approve commands, but the payload is fixed and therefore very limited: imagine having to determine if running a cat command is allowed without the conversation context. This would allow users to have more control over the approval process, and to tailor it to their specific needs and requirements.

Second, more attention should be paid to the accuracy of the classifier model. A good starting point, at least for me, would be the ability to select the model that I want to use for the approval process, for example using cheaper models for less critical tasks, while using cutting-edge models for critical tasks like production deployments.

Finally, those classifier models shouldn't return a single yes/no answer, but a detailed response that can steer both the main model and the user to a better solution. Codex is already doing this to some extent, but the rationale is about whether the action is safe, not whether it is useful. The classifier sees the request and the command the main model wants to run, so it is in a good position to notice when the approach itself is wrong (trying to read a service's logs when the problem was never going to show up there, for example). Instead, the main model keeps circling the same idea with different approaches, burning tokens.

In general, this kind of mechanism will be a must-have in every tool, and the two I use already ship one, so what's left is for them to push each other on how good the classifier actually is.
